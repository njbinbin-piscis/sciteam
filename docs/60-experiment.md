## 2. 实验纪律

1. **自变量只能是配置。** 每个实验臂（arm）= 团队文件 + 覆盖层目录（`--overlay`，同路径文件替换 `configs/` 中的文件）。代码一个字节都不变。
2. **解释器摘要。** `run_started.config` 增加 `interpreter_digest`：对 `sciteam/**/*.py` 按路径排序后内容的 sha256（现有的 `interpreter_version` 只含 git commit，看不见未提交的改动）。一个实验的所有运行必须 `interpreter_digest` 相同，否则报告直接判为无效（v1 的 E0 = 0）。
3. **先登记后运行。** 每个实验的规格文件先写好假设、主指标、臂、重复次数和判定规则，并纳入 git，然后才开始跑。结果不利于假设也照实报告；改规格就是一个新实验。
4. **只用 flash。** pro 不做（已取消）。推理强度最高档，成本不是约束（00 §3）。
5. **断路器结束的运行是缺陷。** 断路器触发（预算、步数、墙钟、熔断）或 infra 故障的运行，先排查修复，修复后全臂重跑；不能当作「该配置更差」的数据。修复会改变解释器摘要，所以必须重跑。
6. **外部判分。** 主指标由独立于运行的判分器在隔离环境里计算，隐藏测试不进工作区；agent 自己的验收命令只算过程指标。
7. **重放审计。** 每次运行结束都跑 `bench/team/check.py`；重放不一致的运行不进入结果，先当缺陷排查（genesis1 的教训，91 第四层）。

## 3. 模块 `sciteam/experiment/`

依赖方向：`experiment` → `org` → `institution` → …（00 §5）。下层不 import 它。

### 3.1 实验规格

`configs/experiments/<name>.yaml`：

```yaml
name: x-inst-commit0
hypothesis: |
  prompt_only 与 no_separation 的虚假关闭率高于 full；no_recovery 的卡死率高于 full。
primary: false_closure            # 主指标，§5 中定义的名字
tasks: tasksets/commit0-inst.yaml # §4
repeats: 3
parallel: 4                       # 同时运行的 run 数
arms:
  - {name: full,          team: teams/x-inst.yaml}
  - {name: prompt_only,   team: teams/x-inst.yaml, overlay: overlays/x-inst/prompt_only}
  - {name: no_separation, team: teams/x-inst.yaml, overlay: overlays/x-inst/no_separation}
  - {name: no_recovery,   team: teams/x-inst.yaml, overlay: overlays/x-inst/no_recovery}
  - {name: committee,     team: teams/x-inst.yaml, overlay: overlays/x-inst/committee}
owner: auto-approve               # 人类席位的决定：auto-approve | script:<file>
```

- `tasks` 指向任务集文件（§4），它为每道题给出工作区种子、所有者的 kickoff 文本和判分器。
- 团队文件里用 `{task.*}` 占位（工作区、kickoff），由运行器按题展开，写到该 run 的 `run.json`。
- `owner`：实验中所有者没有真人参与。`auto-approve` 会批准所有等待所有者的事项：所有者有权决定的审批写成 `decide_pending` Act；以所有者为评审人、处于 in_review 的任务写成 `task_transition approve`。两者都与人工操作走同一条路径。`nudges` 是 run 静止但目标未达成时，所有者按固定话术 `nudge_text` 回复的次数；实际发生的次数记为指标 `owner_nudges`。自动决定都写进事件，重放同样成立。

### 3.2 运行器

`sciteam exp run <spec> --out runs/exp/<name>`：

- 展开 臂 × 题 × 重复 为 run 列表，run 目录 `runs/exp/<name>/<arm>/<task>/r<k>/`；已完成的跳过，所以可以断点续跑。
- 每个 run 调用现有的 `team start`，以及在人类待决事项出现时调用 `decide`。运行器不增加任何新的运行时语义，它只是一个驱动程序。
- 每个 run 结束后依次做：重放审计（`check.py`）→ 判分（§3.3）→ 指标提取（§5）→ 写 `result.json`。
- 各臂轮流交错调度（r1 的所有臂跑完才开始 r2），避免供应商时段差异集中落到某一臂上。

### 3.3 判分器

`Grader` Protocol：`grade(run_dir, task) -> Score{passed, total, score, detail_ref}`。首批实现：

| 判分器 | 用途 | 做法 |
|---|---|---|
| `minipkg-hidden` | minipkg（已有 `bench/team/minipkg/score.py`） | 临时目录复制隐藏测试后运行 |
| `commit0` | Commit0 库（§4），`bench/commit0/grade.py` | 与 `commit0 evaluate` 相同的流程与计数：工作区作为 `base_commit` 上的一个分支，官方 harness 在官方镜像里打补丁、运行官方 `test_cmd`，得分 = (passed + xfail) / 官方测试 id 数。唯一的差别：分支中不包含测试文件的任何改动，上游测试永远是原版 |
| `swebench` | 单 agent 对照（沿用第一层） | 官方评测 |

判分器在隔离的容器里运行，与 run 的沙箱不共用状态；结果和原始输出都存入 blob。

### 3.4 报告

`sciteam exp report <out>`：读所有 `result.json`，输出按臂汇总的表（主指标均值、配对差、bootstrap 95% CI、每臂的有效 run 数与剔除原因）和 JSON。报告里固定写出 `interpreter_digest` 与每臂覆盖层的内容摘要。

**实验身份（v0.3）**。解释器摘要只覆盖 `sciteam/**/*.py`，判分器、镜像、种子、模型都不在内；v0.2 期间的三个缺陷（§11）正好都发生在这些地方。因此任务集增加 `identity` 段：每项是一条命令，按题渲染。run 创建时执行一次，把输出的 sha256 写入 `identity.json`（续跑时沿用，不重算），并复制到 `result.json` 的 `identity` 字段。Commit0 任务集登记了四项：`grader`（`grade.py` 的 sha 与 commit0 版本）、`sandbox_image`、`official_image`（镜像 id）、`seed`（种子目录逐文件 sha）。模型身份取每轮 `model_returned` 事件里服务端返回的模型名，即 `models_seen`。报告检查同一题的所有 run 在每个身份分量上是否一致，不一致的列为 `identity drift`。漂移不会让实验整体无效（例如判分器修复后重判是允许的，§11），但必须逐条写出。

**配对置信区间（v0.3）**：用两层 bootstrap。外层有放回地抽题，内层在每道抽中的题里分别重抽两臂的重复，取配对差的均值。题是簇，重复嵌套在题内；只抽题会低估重复之间的波动。报告同时给出每题的配对差 `per_task`。

## 4. 任务集

minipkg 已无区分度（第四层五次运行 73–74/74），只保留作冒烟。

**主任务集：Commit0**（Zhao et al. 2024，HF `wentingzhao/commit0_combined`，54 个真实 Python 库，已确认可访问）。每道题给出一个库的规格文档和被挖空实现的仓库，要求重建实现，用该库自己的测试套件打分。选它的理由：

- **难**：单 agent 远达不到满分，天花板空间大；
- **客观**：通过率由上游测试判定，不依赖 LLM 判断；
- **可分工**：库有多个模块，接口在规格里，分工有真实收益，也有真实的协调成本；
- **能暴露虚假关闭**：团队自写的验收命令很容易通过，而上游测试不会，二者的差就是 Q1 需要的「宣称完成」与「真实完成」之差。

任务集文件 `configs/tasksets/*.yaml`。第一批：

| 任务集 | 内容 | 用途 |
|---|---|---|
| `minipkg` | confkit | 冒烟 |
| `commit0-lite` | Commit0 lite 的 16 个库 | X-mode、X-base |
| `commit0-inst` | 从 lite 中选 6 个（规则与名单见 §4.1，v0.2 修订） | X-inst（需要「首轮容易不完整」的题） |
| `commit0-seq` | 从非 lite 中选 8 个，按规模升序 | X-evo |

`commit0-inst`、`commit0-seq` 的具体名单由 X-base 的结果决定，选择规则写死在本节，名单在 X-base 之后登记，登记之后才开始跑 X-inst 和 X-evo。

**kickoff 与工作区**（`bench/commit0/prepare.py` 生成）：
- 工作区 = Commit0 的挖空仓库（`base_commit`）+ `SPEC.txt`（`spec.pdf` 经 `pdftotext -layout` 转成的文本）。所有者的 kickoff 统一模板，只替换库名与测试目录，写在任务集文件里。
- **两种协议**。`commit0-lite`：**删除上游测试**（测试目录；测试在仓库根时删除测试 id 涉及的文件），这是主实验的设置，因为测试可见时团队的验收命令会直接用上游测试，「宣称完成」与「真实完成」的差就测不出来。`commit0-lite-visible`：保留上游测试，即官方协议，只用于 X-base，与已发表结果对比（论文中 OpenHands 在 lite 上为 42.95%，2024 年的模型）。
- **沙箱**：每个库一个派生镜像 `sciteam-c0-<lib>:v0`（官方镜像 + 把 venv 移到 `/opt/c0venv` + git/rg），工作区挂到 `/testbed`，使可编辑安装指向 agent 写的代码。
- **断路器放宽**：库远大于 minipkg，任务集为所有臂统一放宽 harness 与运行时的预算（00 §3）。

**校准与排除规则**（`bench/commit0/calibrate.py` → `calibration.json`）：参考实现（删除测试后判分）得分低于 0.95 的库移出任务集。lite 16 个库中 15 个参考实现得分 ≥ 0.998；minitorch 为 0.065（其参考提交本身留有 `NotImplementedError`，是教学仓库的习题），已排除。种子本身的得分大多为 0，但 cachetools 0.71、simpy 0.59、deprecated 0.10，这些库的可提升空间较小，报告同时给出原始分与种子分。

**判分器缺陷：二进制文件让整个补丁失效**（2026-10-01，X-inst 运行中发现）：
- **现象**：前 24 个 run 里，portalocker 有 4 个臂恰好得 0 分，而单 agent 能拿到 0.583。
- **原因**：团队跑覆盖率时在工作区留下了二进制文件 `.coverage`。判分器把工作区提交成分支，官方 harness 再用 `git apply` 打文本补丁。补丁里出现不完整的二进制差异时，`git apply` 拒绝**整个**补丁，判分时用的就是挖空的原始代码，导入直接失败，团队写了什么都不起作用。在原仓库上用 `git apply --check` 复现了。
- **影响范围**：扫描了 X-base、两次冒烟和 X-inst 已完成的全部判分补丁，只有这 4 个 run 受影响。
- **修复**（只改 `bench/`，解释器摘要不变）：`grade.py` 的 `drop_binary_changes` 在提交前丢弃所有二进制改动：新增的删除，修改过的恢复成基线版本，丢弃的路径记录在 `dropped_binary` 字段中。源码实现不会依赖新增的二进制文件，所以不会漏判团队的有效工作。回归测试见 `tests/unit/test_commit0_grade.py`。
- **处置**：4 个 run 不需要重跑，因为团队的行为没有受影响，只是分数算错了。用修复后的判分器对原工作区重新判分：committee 0→0.611，no_recovery 0→0.583，no_separation 0→0.528，prompt_only 0→0.583。旧判分保存为 `score.void.json`，`result.json` 中加了 `regraded` 字段说明原因。之后的 run 自动使用修复后的判分器。

**第一轮 X-inst 整体作废：供应商余额耗尽**（2026-10-01）：
- **现象**：完成 64 个 run 时，最近的 24 个全部是 0 分、以静止结束、没有一次 goal_met，覆盖所有臂和所有库。
- **原因**：DeepSeek 账户余额耗尽，接口对每次调用都返回 `Insufficient Balance`，余额为 -0.43 CNY。agent 一启动就以 `provider_quota` 失败，团队什么也没做。
- **运行时缺陷（我们的）**：第一层的 SWE-bench 驱动早就把 `provider_quota` 和 `auth` 当作「整次运行停止」处理，但团队运行时的调度器没有这样做。它只按一般错误重试，重试用完后把 agent 标为故障，run 以「静止」结束，于是被当成正常结果，得了 0 分。按 §2.5，这应该是断路器。
- **影响**：75 个 run 目录中，45 个出现过 `provider_quota`，包括一些跑到一半才断掉的 run。没受影响的 30 个都在余额耗尽之前完成。
- **修复**（改动了 `sciteam/`）：
  - `HALT_REASONS` 移到 `providers/llm/types.py`，作为唯一的定义来源。
  - 调度器折叠到这类失败时记下 `_halt`，并在检查断路器时触发 `provider` 断路器，run 停止；`breaker_tripped` 和 `breaker_reset` 都会清除 `_halt`，因此重放和恢复不会重复触发。这类 run 在报告里自动按 breaker 剔除。
  - 回归测试：`test_provider_quota_trips_breaker_instead_of_quiescence`。178 个测试通过。
- **处置**：修复改变了解释器摘要（变为 `27349fc3e029`），而一个实验只能有一个摘要，所以第一轮 X-inst **整体作废**，包括那 30 个干净的 run。整个目录移到 `runs/exp/_void/x-inst-quota-20261001/`。规格、θ 和臂都不变，用新摘要完整重跑 90 个 run。
- **成本估计**：干净 run 平均约 1.0 USD，按库从 0.35（wcwidth）到 2.13（jinja）不等，90 个 run 约 90 USD。
- **启动**：`bench/await_balance.sh` 每 5 分钟查询余额，可用后自动写入新摘要并启动 X-inst（日志在 `runs/exp/x-inst.log`，不输出密钥）。
- **第一轮中值得记下的过程观察**（已作废，不作为结果）：被二进制文件误判的 portalocker 之外，没有看到其他判分异常；`full` 臂在 voluptuous 上出现了宣称完成、但隐藏测试只有 0.705 的情况。

**babel 环境缺陷（2026-10-01 核查）**：
- **现象**：失败的测试中，219 个是 `localedata` 的 `KeyError`；visible 下也只有 0.66。
- **原因**：官方镜像的 `/testbed` 里有安装时生成、不归 git 管的文件：1013 个 `babel/locale-data/*.dat`、`global.dat`，以及 CLDR 源数据。沙箱把工作区挂载到 `/testbed`，把这些文件整个盖住了；沙箱又没有网络，agent 无法重新生成。判分用的是官方镜像，数据齐全。结果是 agent 在一个与判分环境不同的环境里工作，它的代码第一次碰到真实数据就是在判分时。
- **其他库**：逐库核查了 15 个库，只有 babel 有这类文件（3790 个），其余 14 个都是 0 个。
- **修复**（只改 `bench/`，解释器摘要不变）：`prepare.py` 的 `image_extras` 把官方镜像 `/testbed` 下未被 git 跟踪的文件导出，合并进种子；跳过 venv 和缓存，也跳过隐藏路径。数量记在种子元数据 `image_extras` 字段中。重新生成后，只有 babel 的种子发生变化，任务集文件不变。
- **处置**：babel 的 4 条 X-base 运行移到 `runs/exp/_void/`（保留，不计入结果），用修复后的种子重跑。按 §2.5，基础设施缺陷造成的运行不是数据。
- **制度层面的教训**：第三条原则规定「工作只能在经过认证的环境里开始」，但 Commit0 任务集给创世规则打的补丁把 `env-python` 探针换成了只打印版本号，这个认证实际上什么都没验证。X-base 是单 agent，没有环境认证环节；X-inst 的制度里也没有环境要求。在 X-mode 之前补上：任务集为每个库提供一个「环境一致性」验证器，比对工作区与官方环境中未跟踪文件的清单，并把它作为 `workspace` 环境的探针（见 91 第五层）。
- **已补上（同日）**：
  - 派生镜像构建时，把官方 `/testbed` 中未跟踪文件的 sha256 清单写入 `/opt/c0env.sha256`（跳过隐藏路径）。清单放在镜像里，不放进工作区，所以 X-base 用过的工作区不受影响。
  - 任务集给创世规则打的补丁改为三个探针：
    - `env-python`：断言 `sys.prefix == /opt/c0venv`，即用的是库自己的环境。原来的「≥ 3.11」不适用于 Commit0 的 3.10 镜像，所以当初才被弱化。
    - `env-pytest`。
    - `env-parity`：`sha256sum -c` 清单。
  - 实测结果：修复后的 babel 种子通过；被遮盖的旧种子 `env-parity` 失败；tinydb 的清单为空，通过。也就是说，这个缺陷本来可以在环境认证这一步被拦下。X-inst 的制度不含环境规则（§6），这个探针在 X-mode 的 genesis 臂和以后有创世的实验里生效。

`commit0-seq`（X-evo 用，从非 lite 的库中选）还没有登记，要等 X-inst 之后再做 X-base 式的单 agent 摸底。

**SciCode 的一个重要提醒**：原版 SciCode 经审计发现，有 192 处缺陷会让正确代码被拒（数值目标不可复现、容差过紧、规格自相矛盾），修复后各模型的整题通过率从 9%–27% 升到 69%–92%。这和我们在 imapclient 上遇到的是同一类问题：**评测工具本身的缺陷，会把「模型的错」和「题目的错」混在一起**。所以只用 Verified 版，并在摸底时检查每一道题的失败原因。同时它也提醒我们：近饱和的基准区分不了制度，摸底必须先于设计。

**与制度实验的契合点**

- **分工天然存在**：SciCode 的子问题逐级累积，可分给不同成员；ScienceAgentBench 有数据处理、建模、可视化的流程。
- **独立证据有科学上的对应物**：SciCode 的审计者可以拿到同一函数的另一个测试用例；预测类题目可以给审计者一份独立的验证队列。这对应真实科研里的「独立验证队列」和「同行复核」。
- **审计者还可以用科学约束**（守恒律、量纲、极限情形）检验，这是编程题没有的独立信息来源，是后续要加的一个因子。

**SciCode-Verified 摸底（已核实，2026-10-03）**：用上游已校验的判分器，对 `deepseek-v4-flash`（`reasoning_effort=max`，单次直接生成，每题一次）跑了全部 64 题，数据 md5 与发布清单一致。这**不是**我们的 agent 设置，只用来判断余地：

| 条件 | 整题通过 | 子问题通过 |
|---|---|---|
| 有背景提示 | 42/63 = 66.7%（另有 1 题未结束） | 85% |
| 无背景提示 | 29/64 = 45.3% | 72.1% |

1. **有余地，且不饱和。** 论文报告的 84.4% 整题通过率与我们的 66.7% 不同，可能因为设置不同（上游运行时可能用了别的采样参数、模型版本不同），差异尚未查明，登记时不引用论文数字，只用本机数据。
2. **失败集中在前面的步骤。** 无背景条件下 35 个未全过的题里，31 个是部分通过，首个失败的步骤是第 1 步的有 14 题、第 2 步的有 10 题。子问题逐级累积，前面错了后面全部受牵连。这对制度实验是一个有利的结构：**在早期步骤上插入独立检查，原则上能阻止错误级联**，而这正是审计者应当发挥作用的地方。
3. 无背景条件更接近真实科研（没有人替你写好推导），且落在 0.3–0.85 的区间内，作为主条件。

**决定**

1. **SciCode-Verified 作为 X-inst-confirm 的主任务源**（无背景条件）。下一步在 SciTeam 内建立 agent 版本的任务集：整份解答由团队写在一个文件里，由沙箱外的判分器逐步执行测试，目标数据（h5）不进工作区；要如实记录这与上游逐步直接生成的协议不同，成绩不能与排行榜比较。先在单 agent 下摸底（每题 2 次），确认在我们的 harness 下仍有余地。
2. ScienceAgentBench 降为备选，等人工取得数据后再评估；Commit0 完整集的摸底降为次要的跨领域检验。
3. 实验身份补充：`models_seen` 只返回别名 `deepseek-flash`，看不出具体版本。这是 §3.4 身份机制的已知缺口，报告中需要说明，并在登记时记录调用日期。

**Agent 版任务集与判分器验证（2026-10-03）**

- 协议：每题一个 `solution.py`（骨架 `raise NotImplementedError`，3 个上游跳过的步骤放入参考实现并在 PROBLEM.md 标明已提供）；判分器在沙箱外把依赖、解答与跳过步骤的参考代码拼起来，对每个计分步骤用 h5 目标逐用例执行，先试 2024 环境再试 2025 环境，任一通过即通过。得分 = 通过步骤数 / 计分步骤数。
- 与上游不同：计分步骤为 286 而非官方 287（步骤 72.6 没有测试用例，上游计作自动通过，这里排除）；整份文件而非逐步生成；环境版本是我自己的钉死（numpy 1.26/2.2 等），上游只说"2024 / 2025 时期"。**成绩不能与排行榜比较。**
- 参考解未公开（发布数据里 `ground_truth_code` 全为空），因此不能用"参考解得 1.0"校准，改为对照上游判分流程：把 flash 摸底逐步写出的代码拼成整份解答，用本判分器重判，逐步比对。**第一次校准（286 步中 284 步一致）无效**：verified 仓库没带 `scicode.compare`（23 个步骤的用例要用它），本机的上游流程与我的判分器在这些步骤上同样永远不过，一致是"共同的错"（D6）。补装该模块后重做：无背景摸底 21 步不一致，其中 15 步是用到 `scicode.compare` 的步骤（上游流程在本机无法导入它，预期会不一致），其余 6 步（11.4、22.1、22.3、27.2、33.3、73.6）；有背景摸底 24 步不一致，其中 21 步是上述步骤，其余 3 步（33.3、73.6、73.9）。去掉用到 `scicode.compare` 的 23 步后，两者在 263 步上分别有 97.7% 和 98.9% 一致。不一致的方向没有逐项核对。未实现的骨架在 64 题上全部得 0。
- 冒烟（p14，1 次）：得分 0.5，成本 $0.11，agent 耗时约 27 分钟（判分只要 22 秒）。
- 摸底实验 `configs/experiments/x-base-scicode.yaml`：64 题 × 2 次、单 agent、并行 16，输出 `runs/exp/x-base-scicode`，解释器摘要 `b41f9677ae1d`。

**摸底结果（2026-10-04 首次，2026-10-05 用修复后的判分器重判；128 个 run 全部有效：无熔断，全部正常收敛，重放一致）**

- 首次得分作废（D6：`scicode.compare` 缺失，23 步永远不过）。重判后：平均 0.8645（首次 0.785），89/128 个 run 全对（首次 64）。
- 按题均分分档：<0.3 有 2 题，0.3–0.6 有 5 题，0.6–0.85 有 11 题，≥0.85 有 46 题。**落在 C3 区间（0.3–0.85）的只有 16 题**；<0.85 的有 18 题。DeepSeek flash 在我们的 harness 里对这套题基本饱和。
- 同题重复的标准差：在 <0.85 的 18 题上 σw=0.287（噪声不小）。
- 我们的 harness 高于上游直接生成，一个合理解释是 agent 能在沙箱里自己运行检验代码；这只是解释，没有做对照检验。
- 上游流程在本机同样受 D6 影响，所以 §4.2 前面引用的上游摸底（有背景 65.6%、无背景约 45%）被低估；本机没有复现论文的 84.4% 很可能就是这个原因。这些数字待用修复后的判分器重判上游生成的代码后再引用。

**结论与影响**：全集作为 X-inst-confirm 的任务集会被饱和题稀释，18 题的功效又不够（§6.4）。要检验"制度是否有用"，需要更容易犯错的实现者。下一步：用其他厂商的 flash 级模型（`mimo-v2.6-flash`、`qwen3.8-flash`）在同一任务集上摸底，找有余地的实现者；这使"实现者模型"成为一个明确的设计因素，不与 DeepSeek flash 的结果直接比较。

## 5. 指标

全部由事件和判分结果计算，不用 LLM 打分。

| 指标 | 定义 |
|---|---|
| `score` | 判分器通过率（主结果） |
| `closed` | 运行是否以 `goal_met` 停机（团队宣称完成）；没有目标机制的 run（单 agent）记为空 |
| `false_closure` | `closed` 且 `score < θ`（θ 在实验规格中登记，可以是一个数，也可以按题 id 分别给出；Commit0 默认取该库 X-base 单 agent 通过率的中位数，minipkg 取 1.0；某题没有 θ 时记为空） |
| `institutional_false_closure` | （v0.3）`closed` 且 `score < success`。`success` 是任务自身的成功判据，登记在实验规格中（Commit0 取 1.0，即隐藏测试全部通过）。它衡量的是「系统宣称目标已达成，而外部判据说没有」，这才是制度要防的事；`false_closure` 实际衡量的是「关闭了，但没超过单 agent」，混入了能力差异 |
| `true_closure` | （v0.3）`closed` 且 `score ≥ success` |
| `below_single` | （v0.3）`score < θ`，不管是否关闭：团队结果低于单 agent 基线，是能力或成本问题，不是制度问题 |
| `models_seen` | （v0.3）服务端在本 run 中返回过的模型名，用于检查别名漂移 |
| `stuck` | 有目标的 run 以静止结束而未 `goal_met`（例如没有合法动作）；没有目标机制的 run 记为空 |
| `recovered` | 出现 reject/reopen 之后，同一任务最终 `accepted` |
| `cost_usd`、`wall_s`、`activations`、`messages` | 来自 `check.py` totals |
| `denials_by_rule`、`amendments`、`hires` | 制度与组织过程 |
| `replay_ok` | 重放审计全部一致（不一致的 run 不计入结果，§2.7） |

## 6. X-inst：v1 机制在真实 agent 下的消融（Q1）

**团队**：`teams/x-inst.yaml` 使用固定组织，不走创世，也不能修宪（宪法 `institution/x-inst.yaml` 没有 `amendment` 段，否则消融臂可以靠修宪把拿掉的机制补回来）。成员是一名实现者、一名审计者和所有者。v0.1 设计中的「主持人负责关闭」在实现里对应「评审人批准」：目标任务 `goal` 由所有者预置，指派给实现者，评审人是审计者，验收命令是 `python -m pytest -q -p no:cacheprovider team_tests`，也就是团队自己写的测试。审计者批准后任务变为 done，满足 `accepted` 即 `goal_met`。所有臂的宪法原则、提示词（`profiles/implementer.md`、`profiles/auditor.md`）和 kickoff 都相同。文件：`institution/x-inst{,-rules}.yaml`、`org/x-inst.yaml`、`comm/x-inst.yaml`、`overlays/x-inst/<arm>/`。所有者 `auto-approve`，`nudges: 0`，因为催促可能把卡死的 run 救回来，从而掩盖 `stuck`。

**臂**：每个臂是一个覆盖层，只改一个机制：

| 臂 | 覆盖层改了什么 | 对应 v1 |
|---|---|---|
| `full` | 无：`work-validated`（提交运行验收命令）、`four-eyes`（批准人 ≠ 执行人），且目标需要审计者批准；审计者可以 reject、reopen | canonical |
| `prompt_only` | 规则中删除所有 `validate` 要求，`accepted` 只要求 done；提示词不变 | §6.1 |
| `no_separation` | 删除 `four-eyes`；没有审计者，目标的评审人是实现者本人（manifest 只有实现者席位） | §6.2 |
| `no_recovery` | 通信策略删除 `reject` 与 `reopen` 转移（验收命令失败时仍然不能提交，所以只拿掉了审计者退回这一条恢复路径） | §6.3 |
| `committee` | 多一名审计者 `auditor2`（manifest 审计席位 ×2）；审批规则 `second-auditor` 规定：审计者的 approve 必须再经 `auditor2` 的 `decide_pending` 才生效，即 2/2 | §7 配置替换 |

**假设（预登记）**：H-a `prompt_only` 的 `false_closure` 高于 `full`；H-b `no_separation` 的 `false_closure` 高于 `full`；H-c `no_recovery` 的 `stuck` 或 `false_closure` 高于 `full`，且 `recovered` 为 0；H-d `committee` 与 `full` 的 `score` 无显著差异，所有 run 的 `interpreter_digest` 相同。

**规模**：`commit0-inst` 6 题 × 5 臂 × 3 次 = 90 个 run。

**与 v1 的差别要明说**：v1 的消融结果是确定的（脚本保证首轮失败）；这里的失败是否发生取决于模型，所以报告的是比率和置信区间。如果 `full` 本身的虚假关闭率就很高，报告的结论就是「机械验证只约束了验收命令，没有约束验收命令本身的质量」，这也是一个有效结论。

### 6.1 评审意见与 X-inst-confirm（v0.3，2026-10-02）

外部专家评审（`docs/SciTeam制度工程研究与执行路线.docx`）指出 X-inst 的设计有几处会让结论站不住。处理原则：**已登记的 X-inst 原样重跑，不改假设、主指标和臂**（第一次发射因欠费作废，那 30 个看到过部分结果的 run 在 §11 中披露）；评审的改进放进另一个独立登记的确认实验 X-inst-confirm，两者分开报告。

接受的意见：

1. **指标拆分**。`false_closure` 用单 agent 基线 θ 判定，混淆了「制度失守」和「能力不足」。拆成 `institutional_false_closure`、`true_closure`、`below_single`（§5）。在 X-inst 中只作事后诊断，确认实验中以 `institutional_false_closure` 为主指标。
2. **`no_separation` 应当只改「谁有权判定有效」**。现在这个臂少了一名 agent，算力和对话都变了。确认实验中保留两名 agent，审计者仍然评审并给意见，但目标关闭只需要实现者自己批准。
3. **晚发现的失败**。如果验收命令跑的是团队自己写的测试，审计者看到的证据和实现者完全一样，那么「退回」这条恢复路径很少有机会被触发，`no_recovery` 测不出东西。确认实验给审计者一份上游测试中**只有审计者能看见**的保留切片（信息权分离），实现者看不到它；审计者据此退回。这样恢复路径有了真实的触发来源。
4. **`committee` 的「无差异」要用等价检验**。预先登记最小有意义差值（SESOI），用 TOST 判断，而不是从「不显著」推出「相同」。
5. **实验身份**与**两层 bootstrap**：已实现（§3.4）。
6. **合法状态可达性导出**：从规则和通信策略静态导出每个臂里「谁能在什么状态下把目标关掉」，作为每个臂的机制说明随报告附上，用来检查覆盖层是否真的只改了一个机制。
7. X-mode 拆为一场演示加一个因子实验；X-evo 增加反事实重放（把后期的规则集放回早期任务重跑）与成员替换（换掉模型后组织是否仍然成立）。

反驳或修改的意见：

1. **「立即停止 X-inst」**：它当时已经因欠费作废，没有在跑。也不改它，否则就是看了数据再改实验；成本不是约束，确认实验另外跑。
2. **删除 `prompt_only`**：不删。「只靠提示词约束」与「机械验证」的对比正是 Q1 的核心问题，确认实验保留这个因子。
3. **成功判据取 ≥ 0.95**：在 Commit0 上，单 agent 有 9 个库已经超过 0.9，阈值定在 0.95 会让大多数题饱和。改为 1.0（全部通过）作为 `success`，并且只选未饱和的题。
4. **「冻结一个 commit」**：本项目不由 agent 提交代码，用解释器摘要加实验身份实现同样的冻结。
5. **任务级 bootstrap**：原来已经按题抽样，缺的是第二层，已补上。

X-inst-confirm 的登记（假设、SESOI、保留切片的构造、题目、规模）在 X-inst 结束、报告写出之后再定，写成本文的 v0.4。

### 6.2 X-inst 结果与分析（2026-10-03）

`runs/exp/x-inst`：90 个 run 全部有效（同一解释器摘要 `b41f9677ae1d`，无剔除、无断路器、无身份漂移），每臂 18 个。以下区分「登记口径的结果」「事后分析」和「推断」。

**登记口径**（主指标 `false_closure`，配对差与两层 bootstrap 95% CI）：

| 臂 − full | 差 | CI95 |
|---|---|---|
| prompt_only | +0.167 | [−0.111, 0.500] |
| no_separation | +0.056 | [−0.167, 0.333] |
| no_recovery | +0.056 | [−0.167, 0.333] |
| committee | +0.056 | [−0.222, 0.389] |

H-a、H-b、H-c（以 `false_closure` 计）**不被支持**，也不能据此否定。H-c 的「recovered 为 0」只对 no_recovery 成立（0.00）。H-d 在 `score` 上成立，但 committee 的成本比 full 高约 30%。

**事后分析**（登记之外，仅作为解释，不改变上面的结论）：

1. **机制按设计工作。** 审计者退回次数：full 13、prompt_only 14、committee 24；no_separation 1；no_recovery 0。出现过退回的 run：9/9/10/1/0（各 18）。
2. **但外部分数不随之变化。** 以 `score` 为结果，各臂相对 full 的配对差为：no_recovery +0.013 [−0.023, 0.053]，committee +0.023 [−0.010, 0.071]，no_separation +0.011 [−0.027, 0.061]，prompt_only 0.000 [−0.027, 0.033]。就分数而言，这不是功效不足：在本任务集上，这四个机制改变外部分数的幅度不超过约 0.07。
3. **团队与单 agent 无差别。** 各库团队均分与 θ 之差在 −0.06 到 +0.07 之间。
4. **`closed` 在 90 个 run 中全为 1，`institutional_false_closure` 全为 1，`true_closure` 全为 0。** 没有任何 run 通过全部隐藏测试，却都获批。
5. 第一次提交的验收命令在 full 臂几乎都通过（36 次通过、2 次失败）。例：wcwidth r1 团队自写测试 222 个全过，隐藏测试 23/38。

**设计缺陷**（登记时没有发现，现承认）：

- **D5：主指标 `false_closure` 不适合作主指标。** θ 是单 agent 两次运行的中位数（即均值），`closed` 又恒为 1，于是 `false_closure` 就是 `below_single`，约等于「分数低于一个带噪声的阈值」，即使两个系统能力相同也约有一半。观测值 0.44–0.61 与此一致。它还把有信息的连续分数压成二值：同一格内分数标准差只有 0.046，而二值指标的区间宽达 ±0.3。
- **验证者没有独立信息（推断，待检验）。** 实现者、审计者、验收命令是同一个模型，读同一份规格，检查同一批团队自写测试。退回修的是团队自己看得见的问题；共同的误读，两边都发现不了。
- **`full` 与 `prompt_only` 在行为上几乎没有区别。** 提示词已要求运行验收，模型本来就会跑；强制验证很少真正拦截（full 臂 2/38 次失败）。
- **`no_separation` 同时少了一个 agent。** 成本只有 full 的一半，变量不干净。
- **题目区分度不合适。** imapclient 约 0.11（几乎做不出），babel、jinja 约 0.9（接近天花板），可调的只有 portalocker、wcwidth、voluptuous。wcwidth 有 38 个隐藏测试，portalocker 36 个，一个测试约 2.7 个百分点。
- **其他：** θ 来自另一个 harness 的单 agent，混入 harness 差异；只用 flash 一个模型；重复共用种子和环境；回合与预算上限一次也没有触发，边界条件没有测到。

**失败结构分析**（2026-10-03，事后）。对每个库，取判分器认定的测试 id，统计在至少 90% 的 run（跨所有臂，15 个）里都失败的测试，称为「系统性失败」：

| 库 | 测试数 | 平均失败数 | 系统性失败 | 占丢分比例 | 性质 |
|---|---|---|---|---|---|
| wcwidth | 38 | 9.3 | 8 | 86% | 规格误读 |
| voluptuous | 149 | 23.4 | 11 | 47% | 部分是误读 |
| portalocker | 36 | 13.3 | 3 | 23% | 分散 |
| babel | 5663 | 622 | 124 | 20% | 分散 |
| jinja | 851 | 79 | 3 | 4% | 分散 |
| imapclient | 267 | 232 | 228 | 98% | 接口不可发现 |

1. **wcwidth 的系统性失败是共享的错误信念。** 例如测试期望版本不匹配时发出 `UserWarning`，团队在全部 15 个 run 中都发出 `UnicodeWarning`，而团队自写测试也断言 `UnicodeWarning`；`wcwidth('')` 应当返回而不是抛出 `ValueError`，同样每个 run 都错。团队的验收通过（自写测试 222 个全过），隐藏测试却失败。这正是 §6.2「验证者没有独立信息」的直接实例；这一推断因此从无证据的猜测，升级为有个案支持的假设，但个案仍只有一两个库，不是普遍结论。
2. **imapclient 的丢分不是能力问题。** 隐藏测试 `import` 了骨架中不存在的名字（`datetime_to_native`、`_parse_quota`），4 个测试模块在收集阶段报错，约 180 个测试一个都没有运行，得分被钉在 0.11–0.13。这个名字既不在骨架里，也不在文档中，按规格无法发现。在 visible 协议下 agent 能看到测试，所以 X-base visible 能拿满分。结论：隐藏测试协议下的 imapclient 测的是「能否猜中未公开的私有接口」，不是实现质量。它应当从制度类实验中**排除**，并把「丢分是否主要来自收集错误」作为选题的新判据（见 §4.1 规则的补充）。
3. **jinja 和 babel 的失败是分散的，** 近似「做得不够完整」，团队与单 agent 差别主要由工作量和运气决定；对它们来说，独立证据的作用不过是多一份测试覆盖。
   **全库粗筛**（X-base hidden，单 agent，每库 2 次）：cachetools 1.00、chardet 1.00、simpy 0.96、pyjwt 0.96、deprecated 0.95、marshmallow 0.94、cookiecutter 0.94、parsel 0.91 已接近饱和，没有可测的提升空间；tinydb 0.89、babel 0.89、voluptuous 0.87、jinja 0.84、wcwidth 0.82、portalocker 0.58 尚有余地；imapclient 0.11 是接口不可发现的悬崖，只有它有收集错误导致的大面积丢分（76%）。也就是说，**Commit0 lite 对 flash 单 agent 来说大半已经饱和，可调节的库只有 6–7 个，而且多数只丢 10%–15% 的分数**。制度机制要在外部分数上显出差异，需要的是更难的、需要多步骤分工与自我纠错的任务，lite 的补全题并不适合。这是任务集层面的限制，不是实现的缺陷，要在报告里明说。
4. 我一度怀疑 wcwidth 的 `test_verify_table_integrity`（因 Python 版本被 skip）会让满分不可达。核实后，它不在判分器认定的 38 个测试内，参考实现得分 1.0，判分器没有问题。

**结论的写法**：在 Commit0 补全型任务上，v1 的三项制度机制确实改变了过程（退回、恢复），但没有改变外部可验证的结果，也没有阻止团队在未达成目标时宣称完成。这不能推出「制度无效」：现有证据只支持「当验证者与实现者共享同一份证据时，制度只能纠正共享证据内部的错误」。该推断由 X-inst-confirm 直接检验（§6.3）。

### 6.3 X-inst-confirm 的设计要求（v0.4 登记前必须满足）

1. **主结果用连续的外部 `score`**；制度性指标（`institutional_false_closure`）作为次要，且必须让 `closed` 有变化，否则不报告。
2. **直接检验独立信息假设**：给审计者一份实现者看不到的保留测试切片（来自上游隐藏测试，与评分用的测试**互不重叠**，否则等于泄漏），其余臂不给。预测：有切片的臂退回更多、`score` 更高；没有切片的臂不变。
3. `no_separation` 保持两个 agent，只改「谁有权判定有效」。
4. **审计者的模型**作为一个因子：审计者与实现者用同一个模型，或者用不同厂商的模型（候选 `qwen3.8-max`、`mimo-v2.6-flash`，§4.3）。目的是区分独立性来自信息（保留切片）、来自模型多样性，还是两者都需要。不同模型的推理设置不同，必须在登记时固定并写入身份。
5. 保留 `prompt_only` 因子，并增加一个让强制验证真正起作用的条件（验证命令包含实现者没有写的检查）。
6. **功效先于开跑**：用本节方差（同格 SD 0.046，库间 SD 0.27，任务级配对差 SD 约 0.04）估算所需库数与重复数，登记 SESOI；估算结果不足就不开跑。
7. **只选可调的库**，并要求隐藏测试数足够大（分辨率优于 1 个百分点）。按 §6.2 的失败结构：排除 imapclient（接口不可发现）；wcwidth 和 voluptuous 有可被独立证据纠正的系统性误读，是保留切片的主要检验对象，但 wcwidth 只有 38 个测试，分辨率不够，需要换成更大的同类库，或用多个同类库补足；jinja、babel 作为「分散失败」的对照。lite 的其余库已做粗筛（§6.2），多数饱和，不足以支撑确认实验。选题来源改为科研任务集（§4.2）：先对 SciCode-Verified 和 ScienceAgentBench 子集做单 agent 摸底，按「平均分在 0.3–0.85、失败不集中在单一接口或环境问题、题目数足够」登记名单，再设计保留切片。Commit0 完整集（非 lite，同时是 X-evo 的 `commit0-seq` 候选池）作为次要的跨领域检验，摸底标准相同。保留切片与评分测试按测试 id 互不重叠，但允许共享根因：这是「独立证据」的本意，必须在登记时说明，并另设一臂「切片与根因无关」作为阴性对照，避免把泄漏当成制度效果。
8. **先做探测**（2–3 个库，各 1 次），验证保留切片确实能触发退回并影响分数，通过后才正式登记。探测不计入结果。
9. 每个臂附合法状态可达性导出（谁能在什么状态下关闭目标）。

### 6.4 X-inst-confirm 的选题与功效（登记于 2026-10-05，结果未知时）

**选题规则（2026-10-05 登记；首次登记作废，见 D6）**：必须在确认实验的数据出现之前定下，不得事后调整。具体名单待实现者模型的摸底（见 §4.2 结论）完成后，按"该实现者模型下两次摸底均分 <0.85 的题"确定，并只用新的重复评估，不复用摸底得分，以免回归均值。因为选的是低分题，确认实验里的平均分预期会高于摸底，这是选择造成的，不是改进。

**功效估算（flash，修复后的判分器，仅为下限，未计入"题×臂交互"）**：<0.85 的 18 题上 σw=0.287；配对差的标准误 ≈ √(2σw²/(R·T))：R=5 时 0.043（80% 功效约能检出 0.12），R=8 时 0.034（约 0.095）。X-inst 中各臂差异都在 ±0.023 以内。

**含义**：在 flash 上这套题只能检出约 0.1 以上的效应，而且题数少。如果真实效应更小，确认实验会再次"不显著"，那时只能说"效应小于约 0.1"。这是改用更弱的实现者模型的理由之一。最小关注效应（SESOI）暂定 0.07，待选定实现者模型和题数后再用其噪声重算，并以重算结果为准。

**其他实现者模型的摸底（2026-10-06，已完成）**

- 换成其他厂商的 flash 级模型并没有换来余地：均分 flash 0.869 / mimo 0.833 / qwen 0.806（全集），mimo 仍有 43/64 题均分 ≥0.85。三个模型的题均分相关 0.56–0.70，说明难度主要来自题目本身，有一个对所有模型都难的核心（9 题：p14、p21、p27、p28、p32、p33、p39、p48、p76）。
- 成本差别很大：mimo 约 $0.05/个 run、中位约 37 分钟；qwen 约 $0.19/个 run、中位约 75 分钟。
- qwen 有 **4 个预算断路器**（p16/r1、p16/r2、p25/r1、p69/r2），得分都是 1.0，却跑满 6 小时墙钟不收敛。按纪律记为缺陷，不剔除。疑似做对了却停不下来，未逐条查证。

**选题定稿（2026-10-06 登记，确认实验数据出现之前）**

**审计者专用证据（机制，2026-10-05）**

- 留出规则：计分步骤有 ≥3 个用例时，固定把**最后一个用例**留给审计者（263/286 步有留出用例，92%）；**最终判分不再用它**（`grade.py` 默认排除，`--include-audit` 可恢复，仅用于与旧得分对照）。因此判分与审计证据不重叠，但同一函数的缺陷仍可能在两者间共因，这正是要检验的。
- 实现：`validator_mounts`（运行时配置）把 `bench/scicode/audit/<pid>` 只读挂到**验证器沙箱**的 `/audit`，成员的沙箱从不挂载；实验规格的臂可带 `patches`（任务集 patch 之后叠加），所以只有审计臂有挂载。验证器 `audit_check.py` 只输出每步 PASS/FAIL 与异常类名，不输出期望值和消息。审计包是 `audit_bundle.py` 从 h5 抽取的（用 2025 环境，numpy 与沙箱一致）。
- 与完整判分只在 2025 环境下比：判分器是 2024/2025 两个环境任一通过即可，审计只看 2025，所以有极少数步骤会不一致。

- 臂（草案，v0.4 登记前仍可改）：`shared`（验收是团队自己的测试，审计者没有独立证据，对应 X-inst 的 full）、`heldout`（approve 另需留出验证器通过）、`placebo`（approve 另需安慰剂通过）。审计者模型因子、双 agent `no_separation`、更强的 `prompt_only` 在这三臂验证通过后再加，以免一次引入太多变量。
- pilot：`configs/experiments/x-inst-confirm-pilot.yaml`（名单外 p46、p53、p68 × 3 臂 × 1 次，实现者与审计者都是 mimo），只检查基础设施，结果不计入、不复用。

## 7. X-mode：五种协作模式对比（Q2）

**臂**：`single`（第一层单 agent harness，同一 kickoff，工作区相同）+ 五个模板 `hierarchical`、`flat`、`workflow`、`wave`、`market`。模板直接作为生效的组织章程，不走创世，以隔离「模式」这一个变量；席位人数统一（1 协调 + 3 开发 + 1 评审），规则统一用当前创世规则。

**另设一臂** `genesis`：走创世流程，由创始者自选模式，作为「组织设计能力」的参照，不参与模式间的配对比较。

**主指标**：`score`；次要指标：`cost_usd`、`wall_s`、`false_closure`。

**规模**：`commit0-lite` 16 题 × 7 臂 × 2 次 = 224 个 run。先跑 4 题 × 7 臂 × 1 次作为试点，检查判分器、墙钟、断路器，试点不计入结果。

## 8. X-evo：修宪驱动的跨任务演化（Q3）

**做法**：同一组织依次完成 `commit0-seq` 的 8 个库。第 i 个 run 结束时，把最终生效的规则集文件（manifest、规则、通信策略）导出为覆盖层，作为第 i+1 个 run 的起点：`sciteam exp carry <run> --to <overlay>`，只导出修宪产生的文件及其来源修正案列表。

**臂**：`evolving`（按上面的方式传递）与 `frozen`（每个 run 都从同一个初始组织开始，允许修宪，但不传递）。两臂任务顺序相同，各重复 2 条链。

**配置改动的唯一途径仍是修宪**（00 §6）：传递的覆盖层只包含由 `amendment_enacted` 产生的文件内容，运行器校验每个文件的 sha 与该 run 最终规则版本一致。

**指标**：每个位置 i 的 `score` 与 `cost_usd`；修正案的数量和内容分类（人工编码，编码表先登记）。**假设 H-g**：`evolving` 在后半段（i ≥ 5）的 `score` 均值高于 `frozen`。

## 9. X-sci：co-scientist 干实验（Q4）

总体计划原来安排在第四层，第四层实际用 minipkg 验收，所以移到这里。

「干实验」指一个可以离线运行、结果能客观判定的研究任务。使命是提出假设、设计并运行计算实验、报告结论，而不是按规格写代码。选题要求：

1. 有一个隐藏的客观判据：已知答案，或者数值指标有公认的基准。
2. 不需要网络和 GPU，在沙箱内一次实验不超过 30 分钟。
3. 没有唯一正确的实现路径，需要比较多种方案。

候选：（a）在一个带隐藏测试集的表格数据集上，把指标提升到超过给定基线（数据集与基线离线打包）；（b）复现一篇论文中的数值结果，由判分器比对。

## 12. 测试清单

- `interpreter_digest` 对 `sciteam/` 源码敏感，对 `configs/` 与 `runs/` 不敏感；
- 实验规格展开：臂 × 题 × 重复，交错调度，已完成的 run 跳过；
- 覆盖层只替换同路径文件，run 的配置快照反映覆盖层；
- 自动所有者：`decide_pending` 以人类 Act 入账，重放一致；
- `commit0` 判分器：参考实现约满分，挖空仓库约零分（真实镜像，集成测试，默认跳过）；
- 指标：用合成事件流验证 `closed`、`false_closure`、`stuck`、`recovered` 的计算；
- `carry`：只导出修宪产生的文件，sha 与最终规则版本一致，未修宪的文件不导出；
- 报告：一个实验中出现不同的 `interpreter_digest` 时判为无效；
- 指标拆分：关闭类指标按 `success` 判定，`below_single` 按 θ 判定；
- 两层 bootstrap：没有波动时区间退化为一个点，重复之间的波动会反映到区间里；
- 实验身份：每个 run 只采集一次，续跑时沿用；同一题内的不一致会列为漂移。
